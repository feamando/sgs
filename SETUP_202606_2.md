# SGS — Setup guide (June 2026, part 2)

*Windows + RTX 4090. Other platforms are not validated.*

Focused on **an honest castle on a hill**: a visibly understandable
low-fidelity castle with towers, a gate, a domed hill, and trees. No
fibonacci-sphere stand-ins, no blobs, no oversized boxes. Plus a disk
cleanup round (down to 383 GB free of 2 TB, almost all of it Planck and
Hertz checkpoints).

Builds on Raum 1.4 (SETUP_202607.md was the Physical Gaussians track; this
file is the parallel demo-fidelity track). See `roadmap.md` for the full
timeline.

## Why this iteration exists

Raum 1.4 hit its density target (33k-62k splats) and missed its fidelity
target. Scenes render as solid mass now, after the viewer was fixed to size
each splat by its Gaussian scale and draw opaque discs. The shapes are still
blocks. The 1.4 post-mortem isolated the bottleneck to one stage: the
decomposer. It stops three or four levels too high and was trained on generic
trees, so it emits shallow trees with generic node names.

The fix has two halves, sequenced deliberately:

- **Raum 0.5 (product):** a deterministic scene grammar that renders a
  recognizable castle on a hill with no model in the loop. This proves the
  target is reachable with the fill, densify, and render stages we already
  have. The grammar doubles as the training-data generator.
- **Raum 1.5 (model):** retrain the decomposer, narrow to the
  castle/hill/village domain, on deep atomic trees produced by the 0.5
  grammar, so the learned model emits the same structure the grammar proves
  looks right.

0.5 comes first because it de-risks 1.5. If the grammar produces a good
castle, 1.5 only has to learn to reproduce those trees.

## 3. Raum 0.5: the deterministic castle grammar

**Status:** new. The honest target. No model in the loop.

The principle: build a parameterized scene grammar where every leaf is an
atomic part at a scale a primitive can honestly represent. Prove the render
stack can produce a recognizable castle on a hill before asking a model to
generate one. `data/scenes/castle_on_hill.py` is the seed; this generalizes it
into a reusable grammar.

### 3.1 Atomic parts (the vocabulary)

Extend the primitive set so a wall is courses of stone, not a smooth slab.
Each is a small Gaussian cluster, sized small relative to its parent so
densification grows features rather than blobs.

| Part | Shape | Notes |
|------|-------|-------|
| `stone` / `brick` | small box | the atomic unit; walls and towers are built from these |
| `wall_segment` | row of `stone`, with a `crenellation` strip on top | length and height parameterized |
| `crenellation` | alternating boxes (merlon / gap) along the top edge | what makes a wall read as a castle wall |
| `tower_round` | ring of `stone` courses (hollow cylinder) + crenellation ring + optional `cone` roof | corner towers |
| `gate` | wall segment with a rectangular void + arch top | sits in the middle of a wall face |
| `keep` | taller box of `stone` courses | central building |
| `hill` | dome (existing primitive), wider than the castle footprint | castle sits on top |
| `tree_conifer` | trunk cylinder + cone canopy (exists in TEMPLATES) | scatter on the hill |

### 3.2 Compositional rules (spatial constraints)

The grammar encodes how parts relate, which the 1.4 decomposer never learned:

- Four `tower_round` at the corners of a square `wall` ring
- `wall_segment` between each adjacent tower pair
- `gate` replaces the front wall segment
- `keep` centered inside the ring, taller than the walls
- the whole castle sits on top of the `hill` (y-offset = hill height)
- `tree_conifer` scattered on the hill skirt, below the wall base, never
  inside the ring

### 3.3 Build the grammar

```powershell
# New: scripts\castle_grammar.py — parameterized generator
python scripts\castle_grammar.py `
  --preset castle_on_hill `
  --towers 4 --wall-courses 6 --with-gate --trees 8 `
  --output output\castle_05.json
```

### 3.4 Render through the existing pipeline

```powershell
python scripts\infer_decomposer.py `
  --serve --fidelity high --refine-mode sgs `
  --templates data\architecture_gs `
  --scene-file output\castle_05.json   # NEW: bypass the model, load a fixed scene
```

This requires a small addition to `infer_decomposer.py`: a `--scene-file`
flag (and a "Load fixed scene" path in the UI) that skips decomposition and
feeds a hand-built tree straight into the fill -> densify -> refine -> render
stages. This is the 0.5 demo.

### 3.5 Gate (0.5)

- The rendered scene is recognizable as a castle on a hill to someone who was
  not told what it is
- Towers read as towers (vertical, crenellated), walls as walls, gate as an
  opening, trees as trees, hill as raised ground
- No fibonacci-sphere fallbacks fire (every node matches an atomic part)
- No single Gaussian densifies into a blob larger than its part

## 4. Raum 1.5: retrain the decomposer

**Status:** new. Blocked on §3 (the grammar generates the training data).

The decomposer fine-tunes a frozen Planck 1.3 base with a small adapter
(`train_decomposer.py`, 50 epochs, lr 1e-4). Three changes from 1.4: narrow
the domain, deepen the trees, and add compositional supervision.

### 4.1 Generate the training set from the 0.5 grammar

The grammar from §3 is the label generator. Sample thousands of castle / hill
/ village / tower scenes with randomized parameters (tower count, wall length,
tree scatter, hill size, colors), each emitted as a deep atomic tree.

```powershell
python scripts\castle_grammar.py `
  --sample 8000 `
  --domain castle,hill,village,tower,keep `
  --paraphrase `              # 2-3 prompt phrasings per scene for text variety
  --output-dir data\decomposition_trees\castle_15
```

`--paraphrase` pairs each tree with a few natural prompt phrasings ("a castle
on a hill", "a fortress atop a hill", "a hilltop castle with towers") so the
model generalizes over wording, not just structure.

### 4.2 Train

```powershell
python scripts\train_decomposer.py `
  --data data\decomposition_trees\castle_15\train.json `
  --checkpoint checkpoints\planck13\best.pt `
  --save-dir checkpoints\decomposer_15 `
  --epochs 60 --lr 1e-4 --batch-size 4 --max-len 768
```

`--max-len` rises from 512 to 768 because atomic trees are deeper and the
serialized JSON is longer. Watch for truncation: if trees clip at generation
time, raise further.

### 4.3 Compositional loss (optional, if 4.2 plateaus)

If the model nests correctly but places parts loosely (towers off the
corners, gate off-center), add a structural penalty on the predicted tree:
penalize corner-tower positions that deviate from the wall ring, and gates
not centered on a face. This is a tree-level loss, not a pixel loss, so it
stays cheap.

### 4.4 Gate (1.5)

- On held-out castle prompts, the emitted tree has depth >= 3 and reaches
  atomic parts (stone, crenellation, trunk) at the leaves
- Corner towers land at the wall ring corners; gate centers on a face
- Rendered output is recognizable as a castle without manual tree editing
- Generic prompts outside the domain still produce a valid (if generic) tree;
  the narrow training must not break the fallback

## 5. Wire 1.5 into the demo

```powershell
python scripts\infer_decomposer.py `
  --checkpoint checkpoints\decomposer_15\best.pt `
  --tokenizer data\wikipedia\tokenizer.model `
  --serve --fidelity high --refine-mode sgs `
  --templates data\architecture_gs
```

Then type "a castle on a hill with trees" and compare against the §3 fixed
scene. The model output should approach the grammar output. Collapse the
`decomposer` / `planck_decomposer` / `decomposer_15` paths to one canonical
location and update the demo command and §1.1 keeper list.

### 5.1 Scale discipline in the fill stage

Independently of the model, seed leaf Gaussians small relative to their parent
(`_fill_gaussians` and `subdivide_scene.py`) so densification grows features,
not blobs. This is the cheap fix called out in the 1.4 post-mortem and helps
both the 0.5 fixed scene and the 1.5 model output.

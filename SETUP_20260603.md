# SGS — Setup guide (June 3, 2026)

*Windows + RTX 4090. Other platforms are not validated.*

Focused on **accurate, higher-fidelity, more realistic castles**: generate
many different castles and castle elements from text, correctly (prompt
faithful) and closer to real geometry. Raum 1.6 (model accuracy) + Raum 0.6
(realism).

Builds on Raum 0.5 (deterministic grammar, recognizable castle, no model) and
Raum 1.5 (decomposer retrained on the grammar; generates a castle FROM A
SENTENCE). See SETUP_202606_2.md for 0.5/1.5, `roadmap.md` for the timeline.

## Limit reached: hand-tuned grammar is the ceiling (-> Raum 1.7/0.7 systemic)

By 2026-06-03 the pipeline works end-to-end: prompt-faithful element choice
(tower != castle), greedy decoding (no flaky parses), kind-based layout snapping
(4 towers on the ring), oriented-ellipsoid lit splats, openings, and refine OFF
(it was distorting clean geometry). 1.6 (accuracy) is DONE. 0.6 (realism) is
mostly done but its biggest lever -- §5.2 real-scan part routing -- is still
OUTSTANDING (needs the 109-scan library on the 4090).

The proportions we CAN tune -- tower aspect ratio, roof height, hill-vs-castle
-- are all HAND-TUNED CONSTANTS in a procedural grammar
(`scripts/castle_grammar.py`), fixed by eye. That hand-tuning is the ceiling,
and it is exactly why scan-routing (§5.2) matters: real scans ARE correctly
proportioned, so routing parts to them both finishes 0.6 and is the first step
of the 1.7 systemic pivot.

This is the ceiling, and it does not generalize:
- Every new structure (bridge, village, ship) needs fresh hand-authored
  builders + magic numbers + snap rules.
- We override the model's geometry with hardcoded values; the grammar's
  procedural primitives, not the model, cap quality. The model already emits
  clean structure (val_loss 0.107).

Systemic directions for the NEXT iteration (Raum 1.7 model / 0.7 product), not
more grammar tuning:
1. **Learn geometry from real scans, not hand-authored primitives.** The 109
   Sketchfab scans ARE correctly-proportioned towers/walls. Route each part to
   real scan geometry (the deferred §5.2) instead of procedural stone-stacks.
   This is the real answer to "proportions".
2. **Learn proportions/layout in decomposition.** Train the model to emit
   scales/positions the renderer respects, with scan-derived ground truth,
   instead of snapping to constants in post.
3. **Differentiable / render-scored objective.** Score renders against
   reference images and optimize, rather than tuning by eye.

Decision: 1.6 is done (recognizable, prompt-faithful castles). Stop hand-tuning
grammar PROPORTIONS. The next concrete build is §5.2 scan-routing on the 4090 --
it finishes 0.6 AND is the foundation of the 1.7/0.7 systemic, scan-driven
approach. Do that instead of more magic numbers.

## Where 1.5 landed, and what it tells us

1.5 works on the headline prompt: "a castle on a hill" produces a recognizable
castle from text. Two honest gaps showed up on other prompts:

- **Accuracy.** "a wall with a gate" produced a whole castle. "a tower with a
  gate" produced a tower with no gate plus unrequested trees. The decomposer
  was trained on only two templates (castle, tower), castle-dominant, so every
  prompt collapses onto the nearest template. It cannot represent a subset.
- **Realism.** Splats render as flat round discs. Geometry reads as stylized
  blocks, not stone.

Both are addressable without touching the base model (see the assessment).

## Assessment: retrain the decomposer, NOT Planck base

The central decision for this iteration. There are two models, and they are
easy to conflate:

1. **Planck 1.3 base** — the 100M Wikipedia language model (frozen encoder).
2. **The decomposer** — Planck fine-tuned on (prompt -> tree) pairs. This is
   what 1.5 trained. This is what we iterate.

**Every 1.5 failure is a fine-tune DATA problem, not a base-knowledge problem.**
The base LM already understands "a wall with a gate" linguistically. The
decomposer overfit a two-template distribution, so it collapses prompts onto
the nearest template. More + more compositional fine-tune data fixes this
directly. Conclusion: keep Planck 1.3 frozen; retrain the decomposer.

Why NOT retrain the base, point by point (these were the open questions):

- **Cost/risk.** 100M from scratch is GPU-days; the 4090 already OOM'd on
  Planck 1.2. High pain, and it does not address the actual failure.
- **Images/scans cannot go into a text LM.** Planck is a text model. "Add
  castle images and scans to the base" means a vision encoder + multimodal
  architecture: a new model family and a research program, not a 1.6 step.
  Scans inform the geometry/fill stage, not the LM weights.
- **Volume is not the bottleneck; diversity is.** A 100M model on a
  structured-output task does not need gigabytes. It needs compositional
  coverage. ~100-200K DIVERSE records beats 2 GB of near-duplicate castles,
  which would overfit harder and waste train time.

So: the "couple gigs of grammar, no LLM, retrain" instinct is the right
mechanism (deterministic grammar as generator) aimed at the wrong target.
Generate diverse compositional coverage, not raw volume, and fine-tune the
decomposer.

## 2. Compositional grammar: elements as first-class scenes

The 1.5 grammar only produced two whole scenes (castle, tower). 1.6 needs the
grammar to emit EVERY element as a standalone, labeled scene, plus castles
composed from them. This is the accuracy fix.

### 2.1 Element catalog

Extend `scripts/castle_grammar.py` with a builder per element, each usable
both standalone and as a castle sub-part:

| Element | Standalone prompt examples | Notes |
|---------|---------------------------|-------|
| wall | "a stone wall", "a wall with a gate" | with/without gate void |
| gate | "a gate", "a castle gate" | arch + void; can stand in a wall |
| door | "a wooden door" | recessed dark box in a face |
| window | "a window", "an arched window" | recessed opening, optional arch |
| arrow-slit | "an arrow slit" | tall thin recess |
| arch | "a stone arch" | freestanding arch |
| tower | "a tower", "a round tower", "a square tower" | round/square variants |
| keep | "a keep", "a castle keep" | central building |
| gatehouse | "a gatehouse" | gate flanked by two short towers |
| battlement | "battlements", "crenellations" | merlon strip |
| hill | "a hill", "a grassy hill" | dome |
| cliff | "a cliff", "rocky cliffs" | steep rock face |
| tree / woods | "a tree", "a forest", "woods" | conifer; cluster for woods |
| rock / boulder | "a rock", "boulders" | sphere cluster |

### 2.2 Composition rules (unchanged, extended)

Castles remain arrangements: corner towers + walls + centered keep + gate in
front face + optional gatehouse, on a hill or cliff, with optional woods. The
new requirement is that the grammar can also emit any element ALONE, and can
honor counts and presence flags from the prompt spec.

### 2.3 Gate

- Each element builds standalone and renders recognizably via the fill path
- `expand_part` covers every new element (shallow-skeleton inference still works)
- A castle still assembles correctly from the element builders

## 3. Mass training-data generation (diverse, no LLM)

### 3.1 Generator design

Sample over the COMBINATORIAL space, not raw volume. For each record:

- pick a scene archetype (single element | element-with-feature | small
  composition | full castle | castle-with-modifiers)
- randomize structural params (tower count 0-6, with/without gate, trees
  0-12, hill vs cliff, round vs square towers, wall length, colors)
- emit the SHALLOW skeleton (parts as leaves; fits the 512-token context)
- synthesize 2-4 prompt phrasings that DESCRIBE the actual structure, so
  counts and presence are learnable signal, not noise

Prompt text comes from a template + paraphrase table (deterministic, free). A
local LLM for phrasing variety is optional, not required, and never a paid API.

```powershell
python scripts\castle_grammar.py `
  --sample 60000 `
  --domain all `              # whole element catalog + compositions
  --paraphrase `
  --conditioned `             # NEW: prompts describe counts/presence
  --output-dir data\decomposition_trees\castle_16
```

Target ~100-200K records after paraphrase expansion. Watch the token-length
histogram: every skeleton must stay under 512 tokens (the §4.1a constraint
from 202606_2). Log and drop anything over, do not silently truncate.

### 3.2 Prompt-conditioned structure

The key accuracy lever. The prompt must constrain the tree:

- "a wall with a gate" -> a single gated wall on ground, NOT a castle
- "a castle with two towers" -> exactly two towers
- "a fort without trees" -> no tree nodes
- "a tower" -> one tower, no gate, no trees

Generate matched (prompt, structure) pairs across the count/presence grid so
the model learns the mapping instead of collapsing to a template.

### 3.3 Gate

- Element coverage: every catalog element appears as a standalone target
- Count/presence grid covered (0/1/2/many towers, gate yes/no, trees yes/no)
- Token histogram entirely under 512; dropped-record count logged

## 4. Raum 1.6: retrain + constrained decoding

### 4.1 Train (decomposer only, Planck 1.3 frozen base)

```powershell
python scripts\train_decomposer.py `
  --data data\decomposition_trees\castle_16\train.json `
  --checkpoint checkpoints\planck13\best.pt `
  --tokenizer data\wikipedia\tokenizer.model `
  --save-dir checkpoints\decomposer_16 `
  --epochs 40 --lr 1e-4 --batch-size 8 --max-len 512
```

More data, so fewer epochs than 1.5 (watch val loss; early-stop on plateau).
`--max-len 512` is the hard ceiling (model context).

### 4.2 Grammar-validated constrained decoding

In `infer_decomposer.py`, after generation:

- parse the emitted tree; if it fails, repair (close brackets) or re-sample
- validate node names against the element catalog; drop unknown leaves
- optionally snap part positions to the canonical layout (corner towers to the
  ring, gate to a wall center) to remove model placement noise -- this closes
  the "slightly worse than the 0.5 hand-grammar" gap

### 4.3 Gate (1.6)

- "a castle on a hill" still renders a castle (no regression)
- "a wall with a gate" renders a gated wall, NOT a castle
- "a tower with a gate" renders a tower with a gate, no unrequested trees
- "a castle with two towers" renders exactly two towers
- emitted trees parse 100% after the repair/validate pass

masonry, dark window/slit insets -- not flat round dots.

### 5.1 True anisotropic Gaussian splats

The single biggest realism jump. Today: isotropic scale, viewer draws flat
round discs.

- Grammar: emit oriented ellipsoid stones. Wall/floor stones are flat slabs
  (one short axis), tower stones curve with the wall. `GaussianParams` already
  carries `scale` (3-axis) + `rotation` (quaternion); the builders just need to
  set them anisotropically.
- Viewer: render oriented ellipsoid splats, not `gl_PointSize` round discs.
  Either extend the shader to project the 3D covariance to a screen-space
  oriented quad, OR adopt a real gsplat renderer (`gsplat.js` /
  `@mkkellogg/gaussian-splats-3d`) and feed it position + covariance + color +
  opacity. The .ply export already carries the data a real renderer wants.

### 5.2 Real-scan part routing

You have 109 Sketchfab scans in 17 category dirs (already labeled by folder).
You do NOT need in-scan 3D semantic segmentation (hard). Instead:

- map each part-leaf (tower/wall/roof/gate...) to a matched-category scan via
  the existing Chamfer template path (`refine_scene.find_local_templates`)
- compose multi-part scenes by arranging category scans per the grammar
- this gives real geometry per part without a segmentation model

Optional training-data angle (answers "decompose the scans into training
data"): treat each labeled scan as the ground-truth fill for its part name, and
arrange them with the grammar to synthesize realistic composed scenes. The
decomposer still only predicts the skeleton; the scans improve the fill, not
the LM.

### 5.3 Atomic openings

Windows, doors, arrow-slits as recessed dark boxes in wall/tower faces. Biggest
"reads as a real building" detail for the lowest effort.

### 5.4 Shading

Cheap height/normal-based shading + fake ambient occlusion in the viewer so
geometry stops looking flat. Low effort, high perceived-quality gain.

### 5.5 Out of scope (explicit)

- **Physical Gaussians (e_p / materials).** That is about simulation (a ball
  bounces off stone), not visual realism (looks like stone). It has its own
  gate (P6 correlation) and stays Raum 2.0. Do not pull it into 0.6.
- **Multiview / SDS refinement.** Already scaffolded (`refine_multiview`,
  `refine_sds`). Optional stretch for 0.6; pulls photographic detail from a
  prior. Nice-to-have, not a gate.

### 5.6 Gate (0.6)

- Splats render as oriented ellipsoids; walls read as stone courses, not dots
- At least one real-scan part type routed and rendered in a composed scene
- Windows/doors visible as openings
- Side-by-side with 0.5: visibly more realistic, same recognizable castle

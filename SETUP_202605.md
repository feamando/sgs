# SGS — Setup guide (May 2026 edition)

*Supersedes `SETUP_202604.md` for the active workstream.*
*Windows + RTX 4090. Other platforms are not validated.*

This doc is scoped to the tracks queued **now**:

1. §1 — Fresh install / restore a terminal session
2. §2 — Planck 1.3 (Wikipedia base retrain, ~3-7 days in background)
3. §3 — Raum 0.1 (product: compositional scenes, common-object vocab, editable DSL)
4. §4 — Raum 1.1 (model: 1-model bridge + ShapeNet blob library)
5. §5 — Satz 0.1 (product: local demo of Planck 1.3 LM + blobs)
6. §6 — Klang 1.3 (remaining sweep against Variant A)
7. §7 — Hertz 1.2 (1B LM, plain AdamW)

Planck 1.2.x (acceleration-recipe work) was shelved 2026-05-01 after
the SGS-native compound kept OOM'ing even with the 1.2.2 `index_select`
rewrite and Muon regressed by +0.48 nats. The learnings worth carrying
into Hertz 1.2 are captured inline in §7; the exhaustive 1.2 / 1.2.1 /
1.2.2 history lives in `SETUP_202604.md` §6.4 / §6.4b / §6.4c and the
plan docs in `docs/plans/`.

## Run order

> **Planck 1.3 (background training) + Raum 0.1 / Raum 1.1 (foreground)
> → Satz 0.1 → Klang 1.3 remainder → Hertz 1.2.**

Raum is now the foreground priority — it is the most exploratory
and highest-information track, and it doesn't block on GPU-weeks.
Planck 1.3's Wikipedia base retrain runs in the background during
Raum foreground work (~3-7 days of plain-AdamW training; Planck 1.1
itself was ~3 hours on TinyStories, so a 4× corpus scale-up is still
short). Satz 0.1 and Raum 1.1 both consume the 1.3 checkpoint as
their frozen encoder — TinyStories-trained Planck 1.1 was the right
proof that blobs work but the wrong substrate for the "reasoner +
knowledge" pitch.

Klang 1.3's 500-gaussian run landed first and is published against
Variant A as a checkpoint artefact (§6.1). The rest of the 1000 /
2000 / 3000-gaussian sweep is deferred until just before Hertz 1.2
— Klang's pitch value is bounded; Raum's is not. If the 500g result
already clears Variant A's gates, the swimlane can close without
the rest of the sweep.

Raum moves ahead of Hertz 1.2 because the demos are shippable value
that don't consume GPU-weeks, and Hertz 1.2 is expensive enough that
we want every shorter track wrapped up first.

## 2. Planck 1.3 — Wikipedia base retrain (background)

**Status:** open. Plan at `docs/plans/planck_13_plan.md`.

Planck 1.3 retrains the 100M base on English Wikipedia (~4B cleaned
tokens) so both Satz 0.1 and Raum 1.1's frozen encoder have
encyclopedic priors, not TinyStories fairy-tale priors. Runs in
**background** during Raum 0.1 / 1.1 foreground work (§3-§4);
wall-clock is ~3-7 days on the 4090 (Planck 1.1 itself was ~3 hours
at ~1-2B TinyStories tokens, so a 4× corpus scale-up at matched
throughput lands in under a week). Plain AdamW — the 1.2.x accel
recipe is shelved.

Raum 1.1 training runs consume the 4090 episodically (hours, not
days), so the two foregrounds (Raum) + background (Planck 1.3)
coexist on one GPU as long as Raum trainings are gated behind
Planck's eval windows. When Raum 1.1 kicks off a long training run,
pause Planck 1.3 until it finishes. Planck 1.3 has no deadline of
its own; it just has to be ready before Satz 0.1 (§5) starts.

Scope of §2 is the base retrain (1.3.0) + the static Wikipedia blob
index (1.3.1a). The live RSS blob index (1.3.1b) and the full QA eval
(1.3.2) land later, after Hertz 1.2 ships.

### 2.1 Corpus prep — English Wikipedia via HuggingFace `datasets`

One-time fetch of the pre-cleaned, pre-deduplicated Wikipedia
snapshot from <https://huggingface.co/datasets/wikimedia/wikipedia>.
The HF dump is reproducible by `{date}.{lang}` revision id and
skips the XML-dump + regex-extractor path (`wikiextractor` is
broken on Python 3.11+: "global flags not at the start of the
expression" in `extract.py:378`).

Latest English revision as of 2026-05-04: **`20231101.en`**
(6.41M articles, ~20 GB Parquet on disk). Verified against
huggingface.co/datasets/wikimedia/wikipedia.

```powershell
pip install datasets

$revision = "20231101.en"
mkdir data\wikipedia 2>$null
$revision | Out-File data\wikipedia\snapshot_id.txt -Encoding ascii

# One-time download (~20 GB Parquet). The dataset is CC-BY-SA-3.0 + GFDL.
python -c "from datasets import load_dataset; load_dataset('wikimedia/wikipedia', '$revision', cache_dir='data/wikipedia/hf')"
```

Row schema: `{id, url, title, text}` — `text` is clean prose with
markup/references stripped and disambiguation pages dropped. ~4B
tokens at the SGS tokenizer.

If you need a newer revision later, check the dataset page for
newer `{date}.en` configs and bump `$revision`.

### 2.2 Tokenize + pack

Turn the HF Parquet cache from §2.1 into `train.bin`, `val.bin`, and
a 32k SentencePiece tokenizer. One command, reuses the existing
`src/tinystories.py` BPE + binary pipeline (same format `train_lm.py`
already reads via `prepare_data`).

```powershell
python -m src.tinystories `
  --dataset wikipedia `
  --data-dir data\wikipedia `
  --hf-cache-dir data\wikipedia\hf `
  --revision 20231101.en
```

Expected output:
- `data\wikipedia\tokenizer.model` (~2 MB)
- `data\wikipedia\train.bin` (~8 GB, uint16 tokens)
- `data\wikipedia\val.bin` (~40 MB)

Takes ~30-60 min: most of it is SentencePiece training on a 1M
sentence sample, then a single pass of batch encoding.

### 2.3 Launch base retrain (background)

Planck 1.3.0 is a **fresh base retrain**, not a blob-attention
finetune. Use `train_lm.py` (not `train_planck11.py` — that one
expects an existing base checkpoint and does the 2-stage blob
warmup).

```powershell
python scripts\train_lm.py `
  --data-dir data\wikipedia `
  --save-dir checkpoints\planck13 `
  --epochs 3 `
  --mixed-precision bf16
```

Architecture defaults match Planck 1.1: `d_s=128 d_f=1000 n_passes=3
n_heads=4 context_len=512 ffn_mult=4`. `train_lm.py` calls
`prepare_data(--data-dir, --vocab-size, --context-len)`, which now
short-circuits on existing `train.bin` + `tokenizer.model`, so §2.2
is the only data-prep step.

Estimated wall-clock: ~3-7 days (4B tokens at the Planck 1.1
throughput baseline of ~3 hours / ~1-2B TinyStories tokens). Leave
running in the background while Raum 0.1 / 1.1 (§3-§4) is the
foreground. Pause this run when Raum 1.1 kicks off a bridge training
(Raum trainings are hours, not days).

### 2.4 Build the Wikipedia blob index (1.3.1a) — Satz prereq, NOT Raum

> **Raum does NOT depend on this step.** The Wikipedia blob index is
> a prereq for **Satz 0.1 only** (§5). Raum uses Planck 1.3 as a
> frozen *token encoder*; the Raum bridge takes per-token features
> `(d_f=300)` and outputs 3D scene parameters — no blob retrieval
> on that path.
>
> Once `checkpoints\planck13\best.pt` exists, Raum (§3, §4) is
> unblocked. Run §2.4 in parallel with Raum work, or defer it until
> just before Satz.

Once `checkpoints\planck13\best.pt` exists, build the lead-section
blob index. `build_blobs.py` reads `data\wikipedia\train.bin`
directly (no second HF pass) and writes a Faiss index + metadata.

```powershell
python scripts\build_blobs.py `
  --data-dir data\wikipedia `
  --checkpoint checkpoints\planck13\best.pt `
  --n-blobs 200000 `
  --output data\blobs\wikipedia
```

`--n-blobs 200000` is the demo-scale target (enough lead-section
coverage for Satz 0.1 without pushing Faiss past a few GB). Grow
later if eval shows retrieval recall is the bottleneck.

### 2.5 Verify + publish

```powershell
python scripts\evaluate_lm.py `
  --checkpoint checkpoints\planck13\best.pt `
  --val-bin data\wikipedia\val.bin `
  --tokenizer data\wikipedia\tokenizer.model `
  --output results\planck13_eval.json

python scripts\generate.py `
  --checkpoint checkpoints\planck13\best.pt `
  --tokenizer data\wikipedia\tokenizer.model `
  --prompt "The history of the Roman Empire" `
  --max-new 200
```

Gate: generation stays on topic for encyclopedic prompts AND
held-out Wikipedia perplexity is in-line with the 1.1→1.3 scale-up
baseline.

```powershell
git add results\planck13_eval.json docs\plans\planck_13_plan.md
git commit -m "Planck 1.3: Wikipedia base + blob index"
git push
```

Flip `1-planck-1-3` to `done` in `roadmap.md` on pass.

### 2.6 Stop conditions

- If held-out perplexity or an MMLU-lite spot check without blobs
  is worse than Planck 1.1's, abort — tokenizer or harness bug, not
  a corpus problem.
- If wall-clock slips past 10 days, diagnose throughput regression
  before pushing further.

## 3. Raum 0.1 — product: compositional scenes, common-object vocab, editable DSL

**Status:** open. Plan at `docs/plans/d1c_raum_01_plan.md`
(rewritten 2026-05-01 for the 1-model architecture).

Raum 0.0 handled "A [rel] B" on six primitives. Raum 0.1 is a
five-stage rollout (0.1.0 → 0.1.5) that lifts that into 3-object
scenes with a 30-60-class ShapeNet blob library and an editable DSL
("nano-banana edit loop"). **There is no separately-trained Planner
LM anymore.** Planck 1.3 is a *frozen encoder* feeding the Raum
bridge (§4) — token features only, no blob retrieval. Raum does
NOT wait on §2.4 (the Wikipedia blob index, which is a Satz prereq). **Runs in parallel
with Raum 1.1 (§4) — the product stages below consume the model
from §4.**

Rollout (from the plan doc, edited for scope):

| stage | scope | time | deps |
|---|---|---|---|
| 0.1.0 | 3-object data generator + extended direction loss | ~1 session | Raum 1.1.B (§4) |
| 0.1.1 | 30-class ShapeNet blob library live in demo | ~1 week | Raum 1.1.A + 1.1.B |
| 0.1.2 | OOV policy: NN-over-blobs + cosine gate | ~1 session | 0.1.1 |
| 0.1.3 | DSL v1 frozen + read-only DSL panel in demo | ~1 week | 0.1.1 |
| 0.1.4 | Editable DSL tab (graph edits re-run renderer only) | ~1 week | 0.1.3 |
| 0.1.5 | 60-class library + "randomise" + polish | ~1 week | 0.1.4, Raum 1.1.E |

Sharp-version success metric for 0.1.0 / 0.1.1: > 90% direction
accuracy on 3-object val set, > 70% of held-out prompts render
without unresolved warnings.

**The encoder is Planck 1.3.** Planck 1.3 is retraining on Wikipedia
specifically so Raum and Satz have an encyclopedic-prior encoder
instead of a TinyStories one. If 1.3 has finished (§2.3), use it.

Bootstrap escape hatch: if you want to start a Raum stage *before*
Planck 1.3 finishes, you can temporarily point `--encoder-checkpoint`
at `checkpoints\planck11\best.pt` to prototype the data generator /
bridge wiring. Treat that as throwaway — re-train against Planck 1.3
(hours, ~5-10M-param bridge) before any gate or publish.

## 4. Raum 1.1 — model: 1-model bridge + ShapeNet blob library

**Status:** open. Plan at `docs/plans/raum_11_plan.md`. Paired with
Raum 0.1 product stages (§3). Architectural scope:

1. **Frozen Planck 1.3 encoder** feeding the bridge (no separate
   Planner LM; see the 1-model pivot in the plan doc §1). Planck 1.3
   is the intended encoder — the whole point of §2's Wikipedia retrain
   was to hand Raum an encyclopedic-prior encoder. Planck 1.1 is a
   bootstrap-only fallback if 1.3 hasn't finished yet.
2. **Bridge at the "1.1 target" scale**: `d_model=256`, 6 layers,
   8 heads (~5-10M params). The sweet spot for a 30-200-class
   blob library on a 24 GiB 4090 (see plan §3).
3. **ShapeNet Core v2 blob library.** 30 classes first, grow to 60.
   Offline `mesh → Poisson-disc sample → Gaussian cloud` pipeline
   in `scripts/build_blobs_shapenet.py` (new). Pattern mirrors
   `scripts/build_blobs.py`.
4. **Relation graph head** + pair-loss extension from Raum 1.0's
   slot-0/slot-1 bias to all consecutive object pairs. Hungarian
   matching deferred to Raum 1.2.
5. **DSL v1** is a pure function of bridge output (`src/raum/dsl.py`
   new), consumed by the renderer. Editable intermediate for the
   demo edit loop.

### 4.1 Bridge scale

Locked at `d_model=256 n_layers=6 n_heads=8 ffn_mult=4`
(~5-10M params, bf16 on 4090 at batch 128). Rationale: 1.0
baseline (~478K) underfits at 30+ classes; 25M+ variants blow up
the per-pair relation head's `[B, T, T]` activation at T ≥ 16 with
3-object paraphrase. If 30-class blob accuracy is still weak at
this scale, ablate `N_BLOBS=30` vs `N_BLOBS=60` before scaling the
bridge further.

### 4.2 Stage 1.1.A — ShapeNet ingest

One-time download (~5 GB, CC-BY-SA). Curate 30 canonical meshes
matching the Raum 0.1 object vocabulary. Build Gaussian clouds:

```powershell
python scripts\build_blobs_shapenet.py `
  --shapenet-root data\shapenet_core_v2 `
  --categories car,chair,table,lamp,sofa,bottle,cup,guitar,airplane,bookshelf,... `
  --n-points 1000 `
  --out-dir data\blobs
```

Output: `data/blobs/<class>.pt` + `data/blobs/index.json`.

### 4.3 Stage 1.1.B — Bridge train (frozen encoder, blob_id head)

```powershell
python scripts\train_raum_bridge.py --glove data\glove.6B.300d.txt `
  --n-objects-max 3 `
  --encoder-checkpoint checkpoints\planck13\best.pt --freeze-encoder `
  --blobs-dir data\blobs --n-blobs-max 30 `
  --d-model 256 --n-layers 6 --n-heads 8 `
  --save-dir checkpoints\raum_11
```

Watch: `pos` (position MSE, < 0.15), `blob` (blob-id argmax acc,
> 85%), `dir` (pairwise direction acc, > 90%), `rel` (relation
argmax acc, > 85%).

### 4.4 Stage 1.1.C — Relation head + pair loss extension

Single flag on the same command:

```powershell
python scripts\train_raum_bridge.py ... --with-relation-head
```

### 4.5 Stage 1.1.D — DSL v1

New file `src/raum/dsl.py` with `validate(dsl)` and
`bridge_output_to_dsl(out)`. Renderer consumes DSL in
`src/raum/render_3d.py`. No behavioural change to the bridge.

### 4.6 Stage 1.1.E — Grow library to 60 classes

Add 30 more ShapeNet classes. Re-run 1.1.A preprocessing,
re-train with `--n-blobs-max 60`.

### 4.7 Analyze + publish

```powershell
python scripts\analyze_raum_bridge.py `
  --checkpoint checkpoints\raum_11\best.pt `
  --glove data\glove.6B.300d.txt `
  --encoder-checkpoint checkpoints\planck13\best.pt `
  --n-objects-max 3

git add checkpoints\raum_11\best.pt results\raum_11_analysis\ `
  data\blobs\index.json scripts\build_blobs_shapenet.py `
  src\raum\dsl.py
git commit -m "Raum 1.1: frozen-encoder bridge + ShapeNet blob library"
git push
```

Flip `6-raum-1-1` to `done` when 1.1.A through 1.1.D hit their
gates. 1.1.E can land as a follow-up. Hertz 1.2 does NOT block on
this — Raum 1.1 is Raum 0.1's backbone, not a prerequisite for
Hertz.

## 7. Hertz 1.2 — 1B SGS LM, plain AdamW (no accel recipe)

**Status:** unblocked as of 2026-05-01. Decision:

- The Planck 1.2.x acceleration-recipe track is shelved. SGS-native
  compound kept OOM'ing on the 24 GiB 4090 even after 1.2.2's
  `index_select` rewrite (the forward `[B·H, L, k, d_f]` activation
  is itself ~8 GiB bf16 × 3 passes, and Windows' shared-GPU-memory
  spillover masked the overage until it finally exhausted system
  RAM). Muon regressed by +0.48 nats at matched token budget.
- Hertz 1.2 therefore runs on **plain AdamW**, same 3-pass SGS
  architecture as baseline. Wall-clock is slower than the accel
  recipe promised (~10 days for 10B tokens vs. the targeted ~5 days),
  but the numbers are trustworthy.

Full post-mortem at `results/planck_12_2/ablation.json` and
`SETUP_202604.md` §6.4c.

### 7.1 Learnings from 1.2.x worth keeping in Hertz

These three code changes from 1.2.2 stay in the tree and benefit
Hertz 1.2 even though the accel recipe itself is gone:

1. **`MuonWithAuxAdam` subclasses `torch.optim.Optimizer`**
   (`src/optim/muon.py`). Makes the wrapper compatible with
   `LRScheduler`. Kept in case we revive Muon on a Linux box (it
   was a Windows-amplified negative, not categorical); removes zero
   code from Hertz 1.2 if we don't use it.
2. **Flat `index_select` in `_causal_render_sparse`**
   (`src/sgs_lm.py`). Tighter autograd path than advanced indexing
   even though the forward activation size is what actually blew
   up. Keep as the default sparse-render implementation if anyone
   re-enables `--sparse-k`.
3. **Harness masks bogus speedup column**
   (`scripts/validate_planck12.py`). `speedup` is `"—"` unless
   `status ∈ {ok, adopted}` and `last_step >= 0.9 × baseline.last_step`.
   Prevents crashed-at-step-0 runs from advertising multi-×
   wall-clock wins. Port the same guard into any Hertz harness.

**Not carried over**: `--transmittance-loss`, `--sparse-k`,
`--shared-kernel` are off by default and off for Hertz 1.2.
`--adaptive-passes` is inert at the Planck scale and we don't
re-enable it at Hertz scale without new evidence.

## Troubleshooting (quick reference)

Full Windows + CUDA troubleshooting (OOM, compile fallbacks, SSL,
sentencepiece build) is in `SETUP_202604.md` §9. The three most
common ones:

### CUDA out of memory

```powershell
python scripts\train_lm.py --data-dir data\fineweb --batch-size 16
```

If a training run hits OOM and the error text mentions "allocated by
PyTorch" > GPU capacity, Windows is spilling CUDA allocations into
system RAM. Either (a) reduce batch size, (b) set
`$env:PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"` before
launching, or (c) move to a Linux box.

### gsplat won't install

Skip it. Raum PoC-C auto-falls back to a CPU renderer (logs
`Rendering backend: simple alpha-composite (CPU)`). Training works,
just slower.

### PowerShell line continuations

Always use backtick `` ` `` in ```powershell fenced blocks, never
`^` (that's cmd.exe). Existing docs pre-2026-04-28 may still mix
the two — treat any `^` continuation in a PowerShell block as a bug
to fix.

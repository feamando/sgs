## 1. Fresh install / restore terminal session

Do this once after cloning or after a long hiatus (new shell, new
drive, reinstalled Windows, etc.). If you already have a working
`.venv` and `data/` dir, skip to §1.4 (just the imports).

### 1.1 Clone

```powershell
cd C:\Users\YourName\Documents\GitHub
git clone https://github.com/feamando/sgs.git
cd sgs
```

### 1.2 Python 3.12 + venv

Requires Python **3.11 or 3.12** (NOT 3.13, PyTorch Windows wheels
don't ship for 3.13 yet).

```powershell

.venv\Scripts\activate
python --version   # 3.12.x
```

If you only have 3.13 installed, grab 3.12 from
<https://www.python.org/downloads/release/python-3120/> and install it
**alongside** 3.13 with "Add to PATH" checked.

## 2. Klang 1.3 — scale to beat Variant A

**Status:** open. Plan at `docs/plans/klang_13_plan.md`.

Klang 1.2 shipped clean but sat behind Klang 1.1 Variant A
(`stft_3000g`, log-MAE 1.255, MCD 308.9) on absolute quality. Klang 1.3
keeps the 1.2 architecture (complex-valued Gaussians, transmittance
compositing, MRSTFT loss) and scales `n_gaussians` up to 1000-3000
to close the gap.

### 2.1 Smoke (5 min on 4090)

```powershell
python klang\klang_1_2_experiment.py --audio klang\test_clip.wav `
  --n-layers 100 --n-steps 500 `
  --device cuda --out-dir klang\klang_1_3_smoke
```

```powershell
  --n-layers 500 --n-steps 5000 `

python klang\klang_1_2_experiment.py --audio klang\test_clip.wav `
  --n-layers 1000 --n-steps 6000 `
  --device cuda --out-dir klang\klang_1_3_1000g

python klang\klang_1_2_experiment.py --audio klang\test_clip.wav `
```

## 3. Raum 0.1 — product: compositional scenes, vocab, OOV, planner

**Status:** open. Plan at `docs/plans/d1c_raum_01_plan.md`.

Raum 0.0 handled "A [rel] B" on six primitives. Raum 0.1 is a
six-stage rollout (0.1.0 → 0.1.5) that lifts that into 3-object
scenes with a 30-object library and a planner-executor split.
**Runs in parallel with Raum 1.1 (§4) — the product stages below
consume the model from §4.**

Rollout (from the plan doc, edited for scope):

| stage | scope | time | deps |
|---|---|---|---|
| 0.1.0 | 3-object data generator + extended direction loss | ~1 session | Raum 1.1 bridge (§4) |
| 0.1.1 | 30-object procedural template library, retrain bridge | ~1 week | template authoring |
| 0.1.2 | OOV policy: NN-over-templates + cosine gate | ~1 session | 0.1.1 |
| 0.1.3 | DSL v1 frozen, executor consumes DSL | ~1 week | 0.1.1 |
| 0.1.4 | Planck 1.1 planner fine-tune, read-only DSL panel in demo | ~2 weeks | 0.1.3 |
| 0.1.5 | Editable scene-graph UI, reasoning-trace output | ~1 week | 0.1.4 |

Sharp-version success metric for 0.1.0 / 0.1.1: >90% direction
accuracy on 3-object val set, >70% of held-out procedural prompts
render without unresolved warnings.

### 3.1 Stage 0.1.0 — 3-object data + extended direction loss

Drives `src/raum/data.py` and `scripts/train_raum_bridge.py`
through the existing training loop. No new script. Train with:

```powershell
python scripts\train_raum_bridge.py --glove data\glove.6B.300d.txt `
  --n-objects-max 3 `
  --save-dir checkpoints\raum_11_n3
```

Analyzer verifies 3-object direction accuracy:

```powershell
python scripts\analyze_raum_bridge.py `
  --checkpoint checkpoints\raum_11_n3\best.pt `
  --glove data\glove.6B.300d.txt
```

Gate: 3-object direction accuracy > 90%.

### 3.2 Stage 0.1.1 — 30-object procedural library

Template authoring lives in `src/raum/templates.py` (add one entry
per object). After authoring:

```powershell
python scripts\train_raum_bridge.py --glove data\glove.6B.300d.txt `
  --n-objects-max 3 `
  --templates procedural30 `
  --save-dir checkpoints\raum_11_p30
```

### 3.3 Stage 0.1.2 — OOV NN policy

Implement nearest-neighbour lookup over template GloVe embeddings
in `src/raum/bridge.py:assemble_scene`. Gate on cosine > 0.35 (tune
once on held-out OOV words); below → keep 0.0's unresolved warning.

### 3.4 Stage 0.1.3 — DSL v1

Schema in `src/raum/dsl.py` (new). Executor in `src/raum/bridge.py`
rewritten to consume DSL as input instead of a grammar-constrained
prompt. Rule-based `prompt → DSL` shim in `demo/app.py` so the
executor is validated end-to-end before the planner fine-tune exists.

### 3.5 Stage 0.1.4 — Planner fine-tune

Use the existing Planck 1.1 checkpoint. New script
`scripts/train_raum_planner.py` (to be written). Procedural
`(prompt → DSL)` dataset of ~50k samples from the §1 grammar
extended with paraphrase templates. Grammar-constrained decoding at
inference via `jsonformer`-style sampler.

### 3.6 Stage 0.1.5 — Editable graph UI + reasoning trace

Demo split into "prompt" + "scene graph (editable)" tabs. Graph
edits re-run executor only; prompt edits re-run planner + executor.
Planner gains a short reasoning-trace string before the JSON.

### 3.7 Run the demo at any stage

```powershell
python -m demo.app `
  --checkpoint checkpoints\raum_11_p30\best.pt `
  --glove data\glove.6B.300d.txt `
  --template-points 1000 `
  --template-confidence 0.35
```

Opens <http://localhost:8000>.

### 3.8 Publish (per stage)

```powershell
git add results\raum_11_analysis\ checkpoints\raum_11_*\best.pt `
  docs\plans\d1c_raum_01_plan.md
git commit -m "Raum 0.1.X: <stage>"
git push
```

Flip `10-raum-0-1` in `roadmap.md` when the sharp version (stages
0.1.0 through 0.1.4) lands. 0.1.5 can land in a follow-up.

## 4. Raum 1.1 — model: 30-template library + relation graph head

**Status:** open. Paired with Raum 0.1 product stages. Architectural
scope (independent of 0.1 rollout sequence):

1. **30-template library.** Procedural primitive-composed shapes
   authored in `src/raum/templates.py`. One per target object. ~1-2
   days to author 30 assuming primitives (cuboid, cylinder, sphere,
   cone, plane, torus) stay unchanged.
2. **Relation graph head.** Per-pair head that classifies relation
   between any two object tokens. Supervised from the data
   generator's relation labels. Enables the analyzer to verify
   "C is right-of B" at inference on N-object scenes.
3. **Pair loss extension.** Replace the slot-0/slot-1 bias in the
   pairwise-direction loss with pair loss over all consecutive
   object pairs. Hungarian matching is deferred to Raum 1.2.

Architecture stays `d_model=128`, 2 transformer layers, 4 heads
(~478K params). Defaults from Raum 1.0 are correct; only the head
count (template argmax over 30 instead of 6) and the new relation
graph head change.

### 4.1 Train

```powershell
python scripts\train_raum_bridge.py --glove data\glove.6B.300d.txt `
  --n-objects-max 3 `
  --templates procedural30 `
  --with-relation-head `
  --save-dir checkpoints\raum_11
```

Watch: `pos` (position MSE, < 0.1), `tpl` (template argmax acc, >
90% at 30 templates is harder than 6; gate at > 85%), `dir`
(pairwise direction acc, > 90%), `rel` (relation argmax acc from
new head, > 85%).

### 4.2 Analyze

```powershell
python scripts\analyze_raum_bridge.py `
  --checkpoint checkpoints\raum_11\best.pt `
  --glove data\glove.6B.300d.txt
```

### 4.3 Publish

```powershell
git add checkpoints\raum_11\best.pt results\raum_11_analysis\
git commit -m "Raum 1.1: 30-template library + relation head"
git push
```

Flip `6-raum-1-1` to `done` when the relation head holds > 85% on
3-object val set. Hertz 1.2 does NOT block on this — Raum 1.1 is
the executor backbone for Raum 0.1, not a prerequisite for Hertz.

## 5. Hertz 1.2 — 1B SGS LM, plain AdamW (no accel recipe)

**Status:** unblocked as of 2026-05-01. Decision:

- The Planck 1.2.x acceleration-recipe track is shelved. SGS-native
  compound kept OOM'ing on the 24 GiB 4090 even after 1.2.2's
  `index_select` rewrite (the forward `[B·H, L, k, d_f]` activation
  is itself ~8 GiB bf16 × 3 passes, and Windows' shared-GPU-memory
  spillover masked the overage until it finally exhausted system
  RAM). Muon regressed by +0.48 nats at matched token budget.
- Hertz 1.2 therefore runs on **plain AdamW**, same 3-pass SGS
  architecture as baseline. Wall-clock is slower than the accel
  recipe promised (~10 days for 10B tokens vs. the targeted ~5 days),
  but the numbers are trustworthy.

Full post-mortem at `results/planck_12_2/ablation.json` and
`SETUP_202604.md` §6.4c.

### 5.1 Learnings from 1.2.x worth keeping in Hertz

These three code changes from 1.2.2 stay in the tree and benefit
Hertz 1.2 even though the accel recipe itself is gone:

1. **`MuonWithAuxAdam` subclasses `torch.optim.Optimizer`**
   (`src/optim/muon.py`). Makes the wrapper compatible with
   `LRScheduler`. Kept in case we revive Muon on a Linux box (it
   was a Windows-amplified negative, not categorical); removes zero
   code from Hertz 1.2 if we don't use it.
2. **Flat `index_select` in `_causal_render_sparse`**
   (`src/sgs_lm.py`). Tighter autograd path than advanced indexing
   even though the forward activation size is what actually blew
   up. Keep as the default sparse-render implementation if anyone
   re-enables `--sparse-k`.
3. **Harness masks bogus speedup column**
   (`scripts/validate_planck12.py`). `speedup` is `"—"` unless
   `status ∈ {ok, adopted}` and `last_step >= 0.9 × baseline.last_step`.
   Prevents crashed-at-step-0 runs from advertising multi-×
   wall-clock wins. Port the same guard into any Hertz harness.

**Not carried over**: `--transmittance-loss`, `--sparse-k`,
`--shared-kernel` are off by default and off for Hertz 1.2.
`--adaptive-passes` is inert at the Planck scale and we don't
re-enable it at Hertz scale without new evidence.

### 5.2 Prereq: Hertz disk cleanup

Before starting the run, clean the Hertz 1.0 artefacts.

```powershell

Get-ChildItem checkpoints\hertz\*.pt | Select-Object Name, `
  @{N='GB';E={[math]::Round($_.Length/1GB, 2)}}

Remove-Item checkpoints\hertz\trace*.json -ErrorAction SilentlyContinue

# Verify data intact
Get-ChildItem data\fineweb\ | Select-Object Name, `
  @{N='GB';E={[math]::Round($_.Length/1GB, 2)}}
```

Full cleanup details (pytorch-inductor cache, wandb dir, HF cache)
live in `SETUP_202604.md` §8.

### 5.3 Launch

```powershell
python scripts\train_hertz.py `
  --max-tokens 10B `
  --no-compile `
  --keep-last 3
```

- `--no-compile`: `torch.compile` via `triton-windows` is slower
  than eager on 4090 Windows.
- `--keep-last 3`: rotate `step_*.pt` checkpoints, keep only the 3
  most recent (~24 GB instead of unbounded). `best.pt`,
  `epoch_*.pt`, `final.pt` are never rotated.

Estimated wall-clock: ~10 days for 10B tokens on RTX 4090 at baseline
throughput (~11.8k tok/s).

### 5.4 Resume

```powershell
# Weights-only resume (drops optimizer state, LR re-warms).
# This is the path that avoids the fused-Adam throughput regression
# on Windows, see SETUP_202604.md §9 "Hertz throughput collapses on resume".
python scripts\train_hertz.py --warm-start checkpoints\hertz\best.pt `
  --no-compile --keep-last 3
```

## Troubleshooting (quick reference)

Full Windows + CUDA troubleshooting (OOM, compile fallbacks, SSL,
sentencepiece build) is in `SETUP_202604.md` §9. The three most
common ones:

### CUDA out of memory

```powershell
python scripts\train_lm.py --data-dir data\fineweb --batch-size 16
```

If a training run hits OOM and the error text mentions "allocated by
PyTorch" > GPU capacity, Windows is spilling CUDA allocations into
system RAM. Either (a) reduce batch size, (b) set
`$env:PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"` before
launching, or (c) move to a Linux box.

### gsplat won't install

Skip it. Raum PoC-C auto-falls back to a CPU renderer (logs
`Rendering backend: simple alpha-composite (CPU)`). Training works,
just slower.

### PowerShell line continuations

Always use backtick `` ` `` in ```powershell fenced blocks, never
`^` (that's cmd.exe). Existing docs pre-2026-04-28 may still mix
the two — treat any `^` continuation in a PowerShell block as a bug
to fix.

*Supersedes `SETUP_202604.md` for the active workstream.*
*Windows + RTX 4090. Other platforms are not validated.*

This doc is scoped to the tracks queued **now**:

1. §1 — Fresh install / restore a terminal session
2. §2 — Klang 1.3 (scale Klang 1.2 architecture to beat Variant A)

## Run order

> **Klang 1.3 → Satz 0.1 → Raum 0.1 (product) + Raum 1.1 (model) → Hertz 1.2.**

Satz 0.1 is a 2-3-session demo that also validates Planck 1.1 is
the right frozen encoder for Raum 1.1. It has to clear before the
Raum 0.1 rewrite commits architecturally to Planck 1.1 as Raum's
encoder (see `docs/plans/raum_11_plan.md` §1). Raum moves ahead of
Hertz 1.2 because the demos are shippable value that don't consume
GPU-weeks, and Hertz 1.2 is expensive enough that we want Raum out
the door first.

already in the tree) that exposes retrieved blobs alongside the
generated text. No new training. Two to three sessions of work.

## 4. Raum 0.1 — product: compositional scenes, common-object vocab, editable DSL

**Status:** open. Plan at `docs/plans/d1c_raum_01_plan.md`
(rewritten 2026-05-01 for the 1-model architecture).

Raum 0.0 handled "A [rel] B" on six primitives. Raum 0.1 is a
five-stage rollout (0.1.0 → 0.1.5) that lifts that into 3-object
scenes with a 30-60-class ShapeNet blob library and an editable DSL
("nano-banana edit loop"). **There is no separately-trained Planner
LM anymore.** Planck 1.1 is a *frozen encoder* feeding the Raum
bridge (§5). **Runs in parallel with Raum 1.1 (§5) — the product
stages below consume the model from §5.**

Rollout (from the plan doc, edited for scope):

| stage | scope | time | deps |
|---|---|---|---|
| 0.1.0 | 3-object data generator + extended direction loss | ~1 session | Raum 1.1.B (§5) |
| 0.1.1 | 30-class ShapeNet blob library live in demo | ~1 week | Raum 1.1.A + 1.1.B |
| 0.1.2 | OOV policy: NN-over-blobs + cosine gate | ~1 session | 0.1.1 |
| 0.1.3 | DSL v1 frozen + read-only DSL panel in demo | ~1 week | 0.1.1 |
| 0.1.4 | Editable DSL tab (graph edits re-run renderer only) | ~1 week | 0.1.3 |
| 0.1.5 | 60-class library + "randomise" + polish | ~1 week | 0.1.4, Raum 1.1.E |

Sharp-version success metric for 0.1.0 / 0.1.1: > 90% direction
accuracy on 3-object val set, > 70% of held-out prompts render
without unresolved warnings.

## 5. Raum 1.1 — model: 1-model bridge + ShapeNet blob library

**Status:** open. Plan at `docs/plans/raum_11_plan.md`. Paired with
Raum 0.1 product stages (§4). Architectural scope:

1. **Frozen Planck 1.1 encoder** feeding the bridge (no separate
   Planner LM; see the 1-model pivot in the plan doc §1).
2. **Bridge at the "1.1 target" scale**: `d_model=256`, 6 layers,
   8 heads (~5-10M params). The sweet spot for a 30-200-class
   blob library on a 24 GiB 4090 (see plan §3).
3. **ShapeNet Core v2 blob library.** 30 classes first, grow to 60.
   Offline `mesh → Poisson-disc sample → Gaussian cloud` pipeline
   in `scripts/build_blobs_shapenet.py` (new). Pattern mirrors
   `scripts/build_blobs.py`.
4. **Relation graph head** + pair-loss extension from Raum 1.0's
   slot-0/slot-1 bias to all consecutive object pairs. Hungarian
   matching deferred to Raum 1.2.
5. **DSL v1** is a pure function of bridge output (`src/raum/dsl.py`
   new), consumed by the renderer. Editable intermediate for the
   demo edit loop.

### 5.1 Bridge scale

Locked at `d_model=256 n_layers=6 n_heads=8 ffn_mult=4`
(~5-10M params, bf16 on 4090 at batch 128). Rationale: 1.0
baseline (~478K) underfits at 30+ classes; 25M+ variants blow up
the per-pair relation head's `[B, T, T]` activation at T ≥ 16 with
3-object paraphrase. If 30-class blob accuracy is still weak at
this scale, ablate `N_BLOBS=30` vs `N_BLOBS=60` before scaling the
bridge further.

### 5.2 Stage 1.1.A — ShapeNet ingest

One-time download (~5 GB, CC-BY-SA). Curate 30 canonical meshes
matching the Raum 0.1 object vocabulary. Build Gaussian clouds:

```powershell
python scripts\build_blobs_shapenet.py `
  --shapenet-root data\shapenet_core_v2 `
  --categories car,chair,table,lamp,sofa,bottle,cup,guitar,airplane,bookshelf,... `
  --n-points 1000 `
  --out-dir data\blobs
```

Output: `data/blobs/<class>.pt` + `data/blobs/index.json`.

### 5.3 Stage 1.1.B — Bridge train (frozen encoder, blob_id head)

```powershell
python scripts\train_raum_bridge.py --glove data\glove.6B.300d.txt `
  --n-objects-max 3 `
  --encoder-checkpoint checkpoints\planck11\best.pt --freeze-encoder `
  --blobs-dir data\blobs --n-blobs-max 30 `
  --d-model 256 --n-layers 6 --n-heads 8 `
  --save-dir checkpoints\raum_11
```

Watch: `pos` (position MSE, < 0.15), `blob` (blob-id argmax acc,
> 85%), `dir` (pairwise direction acc, > 90%), `rel` (relation
argmax acc, > 85%).

### 5.4 Stage 1.1.C — Relation head + pair loss extension

Single flag on the same command:

```powershell
python scripts\train_raum_bridge.py ... --with-relation-head
```

### 5.5 Stage 1.1.D — DSL v1

New file `src/raum/dsl.py` with `validate(dsl)` and
`bridge_output_to_dsl(out)`. Renderer consumes DSL in
`src/raum/render_3d.py`. No behavioural change to the bridge.

### 5.6 Stage 1.1.E — Grow library to 60 classes

Add 30 more ShapeNet classes. Re-run 1.1.A preprocessing,
re-train with `--n-blobs-max 60`.

### 5.7 Analyze + publish

```powershell
python scripts\analyze_raum_bridge.py `
  --checkpoint checkpoints\raum_11\best.pt `
  --glove data\glove.6B.300d.txt

git add checkpoints\raum_11\best.pt results\raum_11_analysis\ `
  data\blobs\index.json scripts\build_blobs_shapenet.py `
  src\raum\dsl.py
git commit -m "Raum 1.1: frozen-encoder bridge + ShapeNet blob library"
git push
```

Flip `6-raum-1-1` to `done` when 1.1.A through 1.1.D hit their
gates. 1.1.E can land as a follow-up. Hertz 1.2 does NOT block on

## 6. Hertz 1.2 — 1B SGS LM, plain AdamW (no accel recipe)

**Status:** unblocked as of 2026-05-01. Decision:

- The Planck 1.2.x acceleration-recipe track is shelved. SGS-native
  compound kept OOM'ing on the 24 GiB 4090 even after 1.2.2's
  `index_select` rewrite (the forward `[B·H, L, k, d_f]` activation
  is itself ~8 GiB bf16 × 3 passes, and Windows' shared-GPU-memory
  spillover masked the overage until it finally exhausted system
  RAM). Muon regressed by +0.48 nats at matched token budget.
- Hertz 1.2 therefore runs on **plain AdamW**, same 3-pass SGS
  architecture as baseline. Wall-clock is slower than the accel
  recipe promised (~10 days for 10B tokens vs. the targeted ~5 days),
  but the numbers are trustworthy.

Full post-mortem at `results/planck_12_2/ablation.json` and
`SETUP_202604.md` §6.4c.

### 6.1 Learnings from 1.2.x worth keeping in Hertz

These three code changes from 1.2.2 stay in the tree and benefit
Hertz 1.2 even though the accel recipe itself is gone:

1. **`MuonWithAuxAdam` subclasses `torch.optim.Optimizer`**
   (`src/optim/muon.py`). Makes the wrapper compatible with
   `LRScheduler`. Kept in case we revive Muon on a Linux box (it
   was a Windows-amplified negative, not categorical); removes zero
   code from Hertz 1.2 if we don't use it.
2. **Flat `index_select` in `_causal_render_sparse`**
   (`src/sgs_lm.py`). Tighter autograd path than advanced indexing
   even though the forward activation size is what actually blew
   up. Keep as the default sparse-render implementation if anyone
   re-enables `--sparse-k`.
3. **Harness masks bogus speedup column**
   (`scripts/validate_planck12.py`). `speedup` is `"—"` unless
   `status ∈ {ok, adopted}` and `last_step >= 0.9 × baseline.last_step`.
   Prevents crashed-at-step-0 runs from advertising multi-×
   wall-clock wins. Port the same guard into any Hertz harness.

**Not carried over**: `--transmittance-loss`, `--sparse-k`,
`--shared-kernel` are off by default and off for Hertz 1.2.
`--adaptive-passes` is inert at the Planck scale and we don't
re-enable it at Hertz scale without new evidence.

Full cleanup details (pytorch-inductor cache, wandb dir, HF cache)

### 6.3 Launch

```powershell
python scripts\train_hertz.py `
  --max-tokens 10B `
  --no-compile `
  --keep-last 3
```

- `--no-compile`: `torch.compile` via `triton-windows` is slower
  than eager on 4090 Windows.
- `--keep-last 3`: rotate `step_*.pt` checkpoints, keep only the 3
  most recent (~24 GB instead of unbounded). `best.pt`,
  `epoch_*.pt`, `final.pt` are never rotated.

Estimated wall-clock: ~10 days for 10B tokens on RTX 4090 at baseline
throughput (~11.8k tok/s).

```powershell

  --no-compile --keep-last 3
```

## Troubleshooting (quick reference)

Full Windows + CUDA troubleshooting (OOM, compile fallbacks, SSL,
sentencepiece build) is in `SETUP_202604.md` §9. The three most
common ones:

### CUDA out of memory

```powershell
python scripts\train_lm.py --data-dir data\fineweb --batch-size 16
```

If a training run hits OOM and the error text mentions "allocated by
PyTorch" > GPU capacity, Windows is spilling CUDA allocations into
system RAM. Either (a) reduce batch size, (b) set
`$env:PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"` before
launching, or (c) move to a Linux box.

### gsplat won't install

Skip it. Raum PoC-C auto-falls back to a CPU renderer (logs
`Rendering backend: simple alpha-composite (CPU)`). Training works,
just slower.

### PowerShell line continuations

Always use backtick `` ` `` in ```powershell fenced blocks, never
`^` (that's cmd.exe). Existing docs pre-2026-04-28 may still mix
the two — treat any `^` continuation in a PowerShell block as a bug
to fix.

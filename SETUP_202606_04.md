# SGS — Setup guide: Raum toward actual realism (0.7 / 1.7)

*Windows + RTX 4090. Other platforms are not validated.*

Sets the direction for Raum 0.7 (product) and 1.7 (model) after 1.6/0.6 shipped
a recognizable, prompt-faithful "castle on a hill" from text. See
SETUP_20260603.md for 1.6/0.6 and its "Limit reached" section; `roadmap.md` for
status.

## What 1.6/0.6 proved about "realism"

Two hard lessons that shape everything here:

1. **Hand-tuned procedural grammar is the ceiling.** Tower ratio, roof height,
   hill size, wall placement -- all magic constants we picked by eye. It works
   for castles and does not generalize.
2. **"Use real scans" is not realism.** Routing parts to the 109 architecture
   scans rendered WORSE than procedural: they are low-res ruin fragments, and
   stretching them to a part footprint produces mush. Realism is bottlenecked
   by source-geometry QUALITY, not by whether geometry is "real".

## Realism has three separable axes

Conflating these wasted effort in 0.6. Name them; move them independently.

| Axis | Question | 1.6/0.6 state |
|------|----------|---------------|
| **Geometry** | does a tower have real tower shape/detail? | procedural blocks (the ceiling) |
| **Material** | does it look like weathered stone, not flat RGB? | flat per-stone color |
| **Composition** | do parts relate believably (towers ring, windows in rows)? | snapped, decent |

0.7 attacks **material** (cheap, ships now). 1.7 attacks **geometry +
composition** at the root (learned, the real work).

## Raum 0.7 (product): cheap appearance wins, ship now

No new model. Make the EXISTING castle look dramatically better, in parallel
with 1.7's harder work.

### 0.7.1 Per-Gaussian material / spherical harmonics

`GaussianParams` already carries `sh_degree` + `sh_coeffs`. Use them:
- view-dependent shading (SH degree 1-2) so stone catches light as you orbit
- per-stone texture/noise on color (weathering, mortar lines, dirt) so a wall
  reads as aged masonry instead of flat grey
- keep the sun/fill/hemisphere lighting from 0.6

### 0.7.2 Real gsplat renderer  [BUILT 2026-06-04, needs browser verification]

A real Gaussian-splat renderer (`@mkkellogg/gaussian-splats-3d` via CDN) loads
the standard-3DGS `.ply` and rasterizes it with proper anisotropic splatting +
SH. Implemented as a STANDALONE page (`/splat`), not an in-place swap, so the
known-good ellipsoid view at `/` is untouched as a fallback. Routes added:
`/scene.ply` (inline PLY) and `/splat` (the viewer); the main demo has an
"Open Gaussian-splat view" link.

The PLY export is already Kerbl-et-al-compliant (src/export/ply.py: f_dc from
RGB, scales, quats, opacity), so the renderer should load it directly. If the
CDN import or PLY `format` arg mismatches the library version, that page fails
gracefully (status line shows the error) and the ellipsoid view still works.

**Commands** (main `.venv`, no checkpoint needed -- `--scene-file` serves a
fixed pre-built scene with no model in the loop):

```powershell
.venv\Scripts\Activate.ps1
python scripts/infer_decomposer.py --scene-file output/castle_06.json --serve --port 8003
```

Then in the browser:
- `http://127.0.0.1:8003/`       -> ellipsoid fallback (known-good)
- `http://127.0.0.1:8003/splat`  -> real gsplat renderer (the 0.7.2 deliverable)

If `/splat` shows only the fallback or an error in its status line, the most
likely cause is a `format` arg mismatch with the installed
`@mkkellogg/gaussian-splats-3d` version (fix = bump the `format` int in the
`/splat` page, NOT regenerate the PLY) or no outbound internet for the CDN
import. Confirmed-working version pin goes here once verified on the 4090.

### 0.7.4 Densify + flatten-to-surface (scripts/densify_flatten.py)

A generic appearance post-process on the flat Gaussian cloud (material axis, no
proportions). Closes the "grid of round stones" gap. Four uniform global knobs,
no per-part tuning (that ceiling -> 1.7):

```powershell
# densify x10, flatten disks to the surface, weather the colour:
python scripts/densify_flatten.py --in output/castle_06.json `
  --out output/castle_06_dense.json --densify 10 --flatten 0.4 --weathering 0.3 --stats

# OR target a total splat count (derives the densify factor from input size):
python scripts/densify_flatten.py --in output/castle_06.json `
  --out output/castle_06_dense.json --splats 30000 --density 1.3 --flatten 0.5 --weathering 0.3 --stats

# serve and eyeball at /splat:
python scripts/infer_decomposer.py --scene-file output/castle_06_dense.json --serve --port 8003
```

The same 4 knobs are wired as LIVE SLIDERS in the "/" UI (Total splats /
Density / Flatness / Weathering), applied server-side via /decompose -- so you
can re-tune without the CLI. Hard-won settings that matter (don't relive them):
- **opacity: keep clones near-opaque (floor 0.8).** A stone castle is SOLID;
  the front splat must win. "Conserve coverage" splitting (a=1-(1-a0)**(1/k))
  drops each clone to ~0.19 -> see-through -> the gsplat view goes CLOUDY.
- **jitter clones in 3D, not tangent-only.** Tangent-plane-only jitter puts the
  flattened disks coplanar -> walls collapse to a single edge-on line.

## Raum 1.7 (model): learned geometry via render-scored objective (D + B)

The real break from the ceiling. This is the systemic answer to "we keep
hand-tuning constants".

### The thesis

1.6 made the model reliable about WHAT (it names four towers, four walls, a
keep). We then OVERRIDE its WHERE and HOW-BIG with snapping and magic constants.
1.7 makes the model emit positions AND scales (D), trained by a DIFFERENTIABLE
render scored against a text-image / diffusion prior (B). Proportions become
learned-to-look-right end to end. The snapping scaffolding falls away.

### Why D alone is a trap

Training the model to emit proportions using the GRAMMAR's own constants as
ground truth just moves the magic numbers into the weights -- circular, zero
gain over snapping. D only pays off coupled to a NON-CIRCULAR signal:
- a render-scored objective (B), or
- proportions measured off GOOD assets (not the 109 ruins).

So 1.7 is D+B, not D.

### Components needed

1. **Differentiable splat renderer.** Render the emitted Gaussians to an image
   with gradients flowing back to positions/scales/colors. (gsplat has a
   differentiable path; or a minimal custom one.)
2. **A prior to score against.** A text-to-image diffusion model providing an
   SDS-style gradient ("does this render look like the prompt?"). The
   `refine_scene.refine_sds` stub is the starting point (needs diffusers).
3. **Decomposer head for geometry.** Extend the model to output per-part
   position+scale as continuous values, trained against the render objective
   rather than snapped.

### Staging (de-risk like 0.5 did for 1.5)

- **Stage 1:** stand up the differentiable renderer + SDS loss on a FIXED
   hand-built scene (no model). Prove the gradient improves a scene's
   appearance against a prompt. This is the 0.5-style "is it even reachable"
   check.

   **Commands** (`scripts/sds_refine.py`). Self-test + photometric run on this
   Mac (CPU, no SD/gsplat); the real SDS run needs the 4090 + `.venv-sds`:

   ```powershell
   # 1. differentiability self-test (CPU, no deps) -- must say "DECREASING"
   python scripts/sds_refine.py --selftest

   # 2. photometric gradient sanity on the real scene (CPU ok, no SD) --
   #    loss should fall toward 0, proving grads reach the splats
   python scripts/sds_refine.py --photometric --scene output/castle_06.json --iters 60

   # 3. full SDS reachability run (4090, .venv-sds with gsplat + SD 1.5).
   #    Positions FROZEN by default (free positions scatter the stones chasing
   #    texture, 2026-06-05 finding); this run = appearance/material win only.
   .venv-sds\Scripts\Activate.ps1
   python scripts/sds_refine.py --scene output/castle_06.json `
     --prompt "a stone castle on a green hill" `
     --iters 150 --img 256 --guidance 40 --out output/castle_sds.json

   # render the refined scene to eyeball the SDS result:
   python scripts/infer_decomposer.py --scene-file output/castle_sds.json --serve --port 8003

   # OPT-IN: let SDS also move positions (the geometry experiment; expect
   #         scatter unless guidance is low + iters short)
   python scripts/sds_refine.py --scene output/castle_06.json --free-positions `
     --guidance 40 --iters 150 --out output/castle_sds_freepos.json
   ```

   **Stage 1 gate: PASSED 2026-06-08 (conditional).** On the 4090 the SDS run
   held geometry (positions frozen worked) and the gradient is COHERENT (colour/
   material moved toward the prompt) -- so SDS-through-a-differentiable-splat-
   renderer is a usable training signal. Reachability proven. Caveats that scope
   Stage 2: (a) it is NOT an appearance WIN over the hand-tuned 0.7 densify/
   weathering -- too colourful, don't use SDS to chase appearance; (b) FREE
   SCALES make flats go stringy -- on a curved surface (towers/roofs) stretched
   splats still tile smoothly, but on a flat wall there is no curvature to
   constrain the stretch direction so splats elongate into strings. Lesson:
   freeze scales for appearance (`--freeze-scales`); SDS earns its keep on
   PROPORTIONS (Stage 2), not texture.

- **Stage 2:** let the objective adjust PART PROPORTIONS only -- the
   position+scale of the ~9 grammar PARTS (4 towers, 4 walls, keep), not the
   ~3000 individual stones. Replaces the snapping scaffolding with learned
   placement.

   **What Stage 2 must dissolve.** The snapping lives in `infer_decomposer.py`:
   `snap_layout()` overrides every recognized part's transform with the hard
   constants in `_CASTLE_LAYOUT` (`_RING=0.7`, all scales `1.0`) and
   `_CONTAINER_XFORM` (`castle` y=0.5 scale 0.9, `hill` y=-0.1). THESE are the
   magic numbers 1.7 exists to kill. The model already EMITS a position+scale
   per part (it is "noisy about WHERE/HOW-BIG"); snapping throws that away. Stage
   2 keeps the model's emitted per-part transform and OPTIMIZES it against the
   render objective instead of snapping it.

   **Design (de-risked, smallest first):**
   1. **Parameterize parts, not stones.** Optimize a low-D vector: per-part
      (x, z, scale) + a few shared (ring radius, castle y-seat, keep height).
      ~9 parts x 3 + ~3 globals ~= 30 numbers. Procedural fill (`expand_part`)
      regenerates stones from the part transform each step, so geometry stays
      coherent BY CONSTRUCTION -- no per-stone scatter, no stringy flats (the
      Stage 1 failure mode is structurally impossible here).
   2. **Render-score the layout.** Same SDS path as Stage 1 (frozen stone
      scales/colours), but gradients flow to the ~30 layout params, not the
      splats. Add a cheap symmetry/overlap regularizer so towers stay on a ring.
   3. **Gate:** the optimized layout matches OR beats hand-snapping (side by
      side vs `snap_layout` output) with NO entry from `_CASTLE_LAYOUT` /
      `_CONTAINER_XFORM` used. If it only matches, that is still a WIN: the
      magic constants are gone, replaced by a render objective that generalizes
      beyond castles.

   Differentiability note: `expand_part` -> stones is not differentiable today.
   Two routes: (a) make a thin differentiable layout->stones map (affine
   placement of fixed per-part stone templates -- gradients flow through the
   placement transform, templates frozen); or (b) finite-difference / CMA-ES
   over the ~30 params using the render score as a black-box objective (no
   autograd through fill needed). (b) is the faster reachability check; do it
   first, move to (a) only if the search is too slow.

   **Commands** (`scripts/optimize_layout.py`, route (b) BUILT 2026-06-08).
   Pure-numpy (mu,lambda) ES over 19 layout params -- no cma/scipy dep. NO
   `_CASTLE_LAYOUT` constant is read; the params are free.

   ```powershell
   # 1. photometric selftest on this Mac (CPU, no SD): start the ES `--perturb`
   #    sigma off a target layout and confirm it CLIMBS back. Reports % error
   #    reduction (the honest metric -- a symmetric castle has many layouts that
   #    render near-identically, so "recover exact params" is the wrong bar).
   python scripts/optimize_layout.py --photometric --perturb 3.0 `
     --iters 45 --pop 16 --img 64 --views 3 --out output/layout_opt.json
   #    Validated 2026-06-08: 55-90% error reduction, scales with start
   #    distance, no premature stall.

   # 2. real SDS layout search (4090, .venv-sds with gsplat + SD 1.5):
   .venv-sds\Scripts\Activate.ps1
   python scripts/optimize_layout.py --sds --prompt "a stone castle on a green hill" `
     --iters 60 --pop 16 --out output/layout_opt.json

   # 3. render the learned layout to judge the gate (serve from main .venv):
   .venv\Scripts\Activate.ps1
   python scripts/infer_decomposer.py --scene-file output/layout_opt.json --serve --port 8003
   ```

   ES-tuning notes (don't relive them): sigma must NOT be driven by elite-std
   (collapses to ~0 once elites cluster -> premature stall). Use a global step
   adapted by a 1/5-success rule (gentle grow 1.05 / firmer shrink 0.85, capped
   [0.2,1.6]) with a sigma floor at 25% of base. The SDS objective is noisier
   than photometric (stochastic timestep per eval) -- judge by the RENDERED
   result vs `snap_layout`, not the score curve.

- **Stage 3:** train the decomposer head to EMIT those learned proportions
   directly, so inference needs no per-scene optimization.

   The model emits per-part transforms ALREADY; today they are discarded by
   snapping. Stage 3 makes them trustworthy:
   1. **Build the dataset from Stage 2.** Run Stage 2 across the prompt set
      (the `castle_on_hill` paraphrases + variants in `castle_grammar.py
      PROMPTS`) to get, per prompt, an OPTIMIZED layout. These are non-circular
      targets (render-scored, not grammar constants) -- the exact thing the
      roadmap says D needs.
   2. **Fine-tune the decomposer** (frozen Planck 1.3 base, same recipe as 1.6
      val_loss 0.107) on prompt -> optimized-layout, so the emitted position+
      scale match the render-good values.
   3. **Remove snapping.** Delete the `snap_layout` call (or gate it OFF) and
      render the model's raw emitted transforms.
   4. **Gate:** model output renders well with `snap_layout` disabled -- towers
      ring, walls meet, keep centered, NO magic constants in the path. This is
      the systemic payoff: the model learned WHERE/HOW-BIG end to end.

   Risk / fallback: if learned proportions regress vs snapping (the 1.6 model
   may be too noisy to hit the targets), keep snapping as a feature-flagged net
   (like 1.6's structural-JSON recovery) and ship Stage 2 as a per-scene
   optimize step while Stage 3 retrains. Never block on Stage 3.

### Parallel cheap win (asset quality, axis = geometry)

Independently of D+B: curate a SMALL set of high-quality architectural Gaussian
splats (10 good towers beat 109 ruins). If good assets exist, scan-routing
(0.6 §5.2, currently opt-in and worse-than-procedural) becomes viable, and also
gives non-circular proportion ground truth for D. Quality over quantity.
